## Write

**A complete draft 0.9** with:

- A new **§0 "Changes from 0.8"** at the top: every change as one entry (section, what changed, the
  evidence-note item or bead or council finding it closes, semantic or editorial, hash impact). Nothing
  changes without an entry. The full version string is `0.9` everywhere, including the envelope part (1),
  so every example's hash changes (§9.2); say so in §0.
- **Group 1, editorial repairs with unchanged local semantics** (note's list): I8 row indices, ISA-10 direct
  versus cyclic hashes, SCC group ordering (bead b-isa-spec-was), empty data spelling (b-isa-spec-oim), I4
  history wording, the accepted r8 suggestions and their positive borrow vector, qreg threading through
  call/ret/branch, literal versus run-time slice offsets, entropy code 10, the zero-cause effective-fault
  repair, every SPEC-QUESTIONS closure, the call-tier policy stated as a table.
- **Group 2, capability contracts** with full normative text, well-formedness, frames/history/reversal
  rules, fault codes, identity impact, and conformance-suite rows: BLK-1 (`qreg[*]`, `qreg.new` with a
  run-time count, `qreg.width`, `qreg.id`, `qreg.from_id`, binding checks), BLK-4 (`qreg.new/free/slice/
  concat` in R with history and the cleanliness inverse), BLK-2 (`budget.mint` on the device), BLK-3
  (`qinplace` with `ins`/`mem`/`args` and the certified inverse pair; §6.1 transfer), ISA-7 (fault-code
  contract for CC/R traps, explicit fault), ISA-8 (reversible failed prefixes; T4 eligibility wording), the
  observable zero fault code. Use the note's proposed sentences as the starting point; where you change
  them, record why in §0 and the progress file. No new numerical fault codes unless unavoidable; no
  narrowing of anything 0.8 permits (rule 10; a stricter rule than 0.8 needs a north-star citation).
- **Group 3, optional efficiency semantics** (I5 identity idle step, I1 pebbled realisations): include as
  §17 deferred decisions with the full-history default, plus the normative hook each would need, unless
  you can write their complete expansion fixtures with hand-derived expected values; the note says they
  are not prerequisites. Everything else marked `efficiency` in the note stays out of 0.9 (record in §0
  as considered and deferred, with the 0.8 construction that keeps the capability).
- **§16.3 examples**: the four 0.8 examples republished under 0.9, and one new example object per new
  instruction family (run-time-width register, R-tier allocation and its reversal, device-minted budget,
  parametrised in-place, failed-prefix reversal, zero fault code), each with hand-derived stated results
  (write the derivation out in the progress file before stating any number). Hashes: compute with
  `reference-interpreter/target/debug/bennett-isa-ref hash <object>` only if that binary accepts the 0.9
  version string and the new instructions unmodified (it will not, for the new instructions); otherwise
  write `sha256: <to be computed by the 0.9 precheck>` and list every such placeholder in the progress
  file. Never edit the crate to make it accept 0.9.
- **§15 conformance suites** extended for every new row, instruction and fault; **§17** updated (closed
  items removed, new deferrals added with defaults); the opcode table §4.8 and grammar §16.2 complete for
  every new form.

Then reread the whole draft as a hostile council member under `rubric-isa.md`: every numerical rule derived,

## Process

- Progress file first (plan of entries), then write; commit owned paths after every group:
  `git add spec/Bennett-ISA-Spec-0.9-draft.md spec/isa-0.8-to-0.9.diff spec/isa-0.9.PROGRESS.md && git
  commit -m "..." -- <those paths>` (retry on index.lock; the other agent commits concurrently). Never push.
- Headless (rule 11); no LLVM tools are needed here. `TMPDIR` inside the repo if you run anything.
- Final message: the §0 change list in brief, the list of examples with verification state (hand-derived
  result, hash computed or placeholder), every departure from the evidence note with reason, open questions
  for the maintainer (numbered, each with your recommendation), and the last commit hash.
